\chapter{Validation and Verification}\label{chap:validation}

\section{Introduction}

This chapter validates the Athena CRDT framework along two topics: (1) formal proofs over the \emph{payload}, \emph{vector clocks}, and \emph{backbone} layers that establish safety properties; and (2) executable demos that witness end-to-end behaviour for representative CRDTs. Our goal is to show that these abstractions introduced in chapters~\ref{chap:payload},~\ref{cha:vectors}, and~\ref{chap:backbone} support concise proofs.

We focus on three key properties:
- \textbf{Convergence (SEC)} for state-based CRDTs: replicas that process the same set of updates (order-insensitively) reach identical states \cite{shapiro2011conflict}.
- \textbf{Progress}: progress holds when deliverable messages exist.
- \textbf{Livelock characterisation}: livelock implies progress (i.e., there are pending messages but the system is stuck repeating a configuration), which is useful to separate fairness assumptions from safety.

\paragraph{Notation.} We write $\mathcal{C}$ for configurations, $\mathsf{net}(\mathcal{C})$ for the multiset of pending messages, and $\mathsf{reduce}^*(\mathcal{C})$ for the maximal delivery closure. Vector clocks use the partial order $\preceq$ and join $\sqcup$ (componentwise $\max$) as in Chapter~\ref{cha:vectors} \cite{lamport1978time,fidge1988timestamps,mattern1989virtual}.

\section{Backbone liveness}

The backbone layer (Chapter~\ref{chap:backbone}) provides generic configuration plumbing. We show the main definitions and liveness facts in small snippets.

\subsection{Configuration and reduction}

We first recall how a backbone configuration is represented as a record of states, clocks, and a multiset of pending messages. This is precisely the structure that all of our CRDTs manipulate.

\AthenaCode{lst:backbone-kfg}{Backbone configuration and reduction}
\begin{lstlisting}[language=Athena,style=athena]
load "../src/framework/backbone.ath"
open Backbone

datatype (Configuration 'State 'Value) :=
  (kfg states:(FMap.Map Ide 'State)
       clocks:Registry
       net:(MSet.MSet (Payload.Message 'Value Clock)))

define (reduce ops cfg) :=
  match (next-message cfg) {
    (none)      => cfg
  | (some msg) => (deliver ops msg cfg)
  }
\end{lstlisting}

The datatype \texttt{Configuration} abstracts the concrete CRDT state and value types and exposes the network as a multiset of messages. The function \texttt{reduce} is a single delivery step: it leaves the configuration as it was when there is no pending messages or it delegates to \texttt{deliver}.

\subsection{Net draining and deadlock}

The shared proof module \\texttt{backbone\_props.ath} specialises this generic interface and proves that repeated reduction drains the network and characterises deadlock.

\AthenaCode{lst:props-reduce-drains}{Backbone: net draining and deadlock}
\begin{lstlisting}[language=Athena,style=athena]
define reduce*-drains-net :=
  (forall ?init:'State ?states:(FMap.Map Ide 'State) ?clocks:Registry
    (forall ?pending:(MSet.MSet (Payload.Message 'Value Clock))
      (= (get-cfg-net (reduce* (payload-ops ?init)
                               (Backbone.kfg ?states ?clocks ?pending)))
         MSet.null)))

\end{lstlisting}

The above definition states that applying \texttt{reduce*} (the reflexive--transitive closure of \texttt{reduce}) to any finite multiset of messages eventually empties the network. It allow us to reason about CRDT behaviour: after delivering all messages, either we are deadlocked (no more work) or there exists a deliverable message.

\subsection{Progress and livelock}

Progress and livelock are also phrased using the generic \texttt{Configuration} type, independently of any particular CRDT.

\AthenaCode{lst:props-liveness}{Backbone: progress and livelock}
\begin{lstlisting}[language=Athena,style=athena]
define progress-equals-reducible :=
  (forall ?S ?R ?N . (= (progress (Backbone.kfg ?S ?R ?N))
                        (reducible (Backbone.kfg ?S ?R ?N))))

define livelock-implies-progress :=
  (forall ?ops ?S ?R ?N .
     ((livelock ?ops (Backbone.kfg ?S ?R ?N))
       ==> (progress (Backbone.kfg ?S ?R ?N))))
\end{lstlisting}

The first equation connects the abstract notion of progress to the operational predicate \texttt{reducible}, defined in terms of \texttt{reduce}. The livelock lemma isolates the role of fairness: if the system is in a livelock, there is still progress in terms of reducible configuration, but termination may require assumptions.

\section{CRDT case studies}

We now instantiate the framework with concrete payloads drawn from the CRDTs that have working demos: GCounter, GSet, OR-Set, and the non-negative counter. Each case shows one or two core definitions or properties and explains how they are expressed using the shared backbone.

\subsection{Grow-only counter (GCounter)}

The GCounter demo (`gcounter_demo.ath`) builds a counter by using a map from actor identifiers to natural numbers and the pointwise maximum as merge operator. The payload layer encapsulates this as a small record of operations.

\AthenaCode{lst:gcounter-ops}{GCounter payload and backbone instance}
\begin{lstlisting}[language=Athena,style=athena]
open GCounter

datatype State := (st value:(FMap.Map Ide N))

define (merge s1 s2) :=
  (st (FMap.map-union-with max (value s1) (value s2)))

define gcounter-ops :=
  (payload-ops State Value merge apply-update)
\end{lstlisting}

The \texttt{State} type and \texttt{merge} function form a join-semilattice where the join is computed pointwise with \texttt{max}. The helper \texttt{gcounter-ops} packages this structure into a \texttt{payload-ops} record, which the backbone then uses to define generic configuration and reduction functions. This pattern is seen across all our CRDTs, the framework expects a small algebraic interface rather than ad-hoc code.

On top of these definitions, the GCounter property module shows how to express ``deliver all messages'' using the \texttt{reduce*} operation.

\AthenaCode{lst:gcounter-props}{GCounter: deliver-all drains network}
\begin{lstlisting}[language=Athena,style=athena]

define (deliver-all cfg) :=
  (reduce* gcounter-ops cfg)

define deliver-all-drains-net :=
  (forall ?cfg:(Backbone.Configuration GCounter.State GCounter.Value)
    (= (get-cfg-net (deliver-all ?cfg)) MSet.null))
\end{lstlisting}

Here, \texttt{deliver-all} is just \texttt{reduce*} instantiated with the GCounter payload. \texttt{deliver-all-drains-net} is a direct consequence of the generic net-draining property, showing how CRDT-specific theorems can be phrased with almost no boilerplate.

\subsection{Grow-only set (GSet)}

The GSet demo (`gset_demo.ath`) is another minimal instantiation: the state is a set of elements, merge is set union, and updates insert new elements.

\AthenaCode{lst:gset-ops}{GSet payload}
\begin{lstlisting}[language=Athena,style=athena]
open GSet

datatype State := (st els:(Set.Set Elem))

define (merge s1 s2) :=
  (st (Set.union (els s1) (els s2)))
\end{lstlisting}

This code mirrors the GCounter setup, but swaps maps for sets. The framework does not need to change: the same backbone and progress lemmas apply, once we provide the appropriate \texttt{merge}.

\subsection{Non-negative counter (NP-Counter)}

The non-negative counter demo (`np_counter_demo.ath`) uses a slightly richer payload to enforce that decrements never make the logical value negative. The core idea is to track separate positive and negative components.

\AthenaCode{lst:np-counter-state}{NP-Counter payload}
\begin{lstlisting}[language=Athena,style=athena]
open NPCounter

datatype State :=
  (np-state pos:(FMap.Map Ide N)
            neg:(FMap.Map Ide N))

define (value st) :=
  (FMap.sum (pos st) - FMap.sum (neg st))
\end{lstlisting}

The \texttt{State} type splits the contribution of increments and decrements, while the function \texttt{value} computes the associated integer. The merge function is again a pointwise maximum on each component; this guarantees monotonicity of both \texttt{pos} and \texttt{neg}, and hence of the overall \texttt{State}. The backbone treats this CRDT exactly like the GCounter, illustrating that richer invariants can be enforced entirely at the payload level.

\subsection{OR-Set and vector clocks}

The OR-Set demos (`orset_demo.ath` and `orset_vc_demo.ath`) showcase the part of the framework that uses vector clocks the most. At the payload level, each element is tagged with a unique identifier and one or two vector clocks: one for additions and, in the VC variant, one for removals.

\AthenaCode{lst:orset-entry}{OR-Set entry structure}
\begin{lstlisting}[language=Athena,style=athena]
datatype Entry :=
  (entry elem:Elem
         add-clock:Clock
         rem-clock:Clock)

define (visible? e clock) :=
  (~ (clock-happens-before (rem-clock e) clock))
\end{lstlisting}

The \texttt{Entry} datatype records both the addition and removal clocks. The predicate \texttt{visible?} states that an entry remains visible at a given replica clock as long as the removal clock does not happen before the replica's clock---that is, the removal has not been causally applied everywhere. This definition relies directly on the vector clock primitives of Chapter~\ref{cha:vectors}.

The VC-based OR-Set also reuses the same backbone configuration and reduction operations. Only the payload (entries, clocks, and visibility predicate) changes.

\section{Equational characterisations}

We summarise the key equations that the implementations satisfy:
- \textbf{Vector clocks:} $C \preceq D \iff \forall i.\ C(i)\le D(i)$ and $(C\sqcup D)(i)=\max\{C(i),D(i)\}$.
- \textbf{Payload monotonicity:} $s \le \mathsf{apply}(s,u)$ ensures inflation of state and idempotence under replay \cite{shapiro2011conflict}.
- \textbf{Net draining:} $\mathsf{net}(\mathsf{reduce}^*(\mathcal{C}))=\varnothing$.
- \textbf{Progress/Deadlock:} $\mathsf{progress}(\mathcal{C}) \equiv \neg\,\mathsf{deadlocked}(\mathcal{C}) \equiv \mathsf{net}(\mathcal{C})\neq\varnothing$.

These align directly with the code equations in \texttt{VCCore}, \texttt{Payload}, and \texttt{Backbone}.

\section{Executable validation}

We validate behaviour via Athena demos drawn from the CRDTs above. Each demo exercises the key behaviours of its CRDT.

\paragraph{Try it.} From the repository root:
\begin{lstlisting}

athena-run src/demos/crdts/gset_demo.ath
athena-run src/demos/crdts/np_counter_demo.ath

For each, the network is reduced to inactivity (\texttt{reduce*}); this confirms convergence and in NP-Counter and OR-Set, the expected interaction between payload invariants and vector-clock metadata.

\section{Threats to validity}

- \textbf{Fairness assumptions.} Livelock exclusion is not proved in general; the framework isolates it via \texttt{livelock-implies-progress} but fairness (or scheduling) must be supplied by the environment.
- \textbf{Model fidelity.} The abstract network is a multiset; real transports may reorder, duplicate, or lose messages. Our proofs assume reliable delivery to match operation-based CRDT requirements.
- \textbf{Finite executions.} Net-draining arguments use structural recursion over finite multisets; infinite streams require reasoning not covered here.

\section{Conclusion}

The validation shows that our implementation realises the algebraic CRDT model: payloads satisfy semilattice and monotonicity laws, vector clocks provide causal metadata, and the backbone composes them to ensure convergence.
